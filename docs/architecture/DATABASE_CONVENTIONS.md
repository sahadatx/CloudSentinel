# Database Conventions

**Status:** Phase 02–03 foundations plus Phase 04 inventory, Phase 05 findings, and Phase 06 risk/compliance/evidence.  
**Authority:** `PROJECT_SPECIFICATION.md`, especially sections 8, 19–22, 28, 50, and 51.

## Platform

PostgreSQL is the primary relational database. SQLAlchemy is the ORM and Alembic manages schema migrations. Phase 02 defines identity, RBAC, tenancy, one-time password reset token digests, and forced-password-change state; Phase 03 adds organization/user/team/AWS-account data; Phase 04 adds scan jobs, assets, and relationships; Phase 05 adds findings and lifecycle events; Phase 06 adds finding evidence, compliance controls/assessments, and finding risk scores. Recovery tokens are global identity records, reference users with cascading deletion, and retain expiry/used/revoked timestamps. Inventory and evidence store selected, normalized values, never full unfiltered provider responses or credentials. Risk scores attach to findings; higher-level aggregates are calculated from active findings to avoid stale polymorphic records.

## Identifiers and ownership

- Use application-generated UUIDv4 identifiers via Python's `uuid.uuid4()` for portable identity generation; PostgreSQL stores them as native UUID values.
- Every tenant-owned resource must have a clear organization ownership path. Organization identity must remain available to enforce isolation in reads, writes, jobs, reports, exports, and audit access.
- Use foreign keys for persisted relationships and define uniqueness constraints for actual domain invariants. Do not introduce soft deletion by default; use it only where justified by the domain and documented.

## Names and timestamps

Use consistent, descriptive, lowercase `snake_case` names for tables, columns, indexes, and constraints. SQLAlchemy metadata uses these constraint templates:

```python
{
    "ix": "ix_%(column_0_label)s",
    "uq": "uq_%(table_name)s_%(column_0_name)s",
    "ck": "ck_%(table_name)s_%(constraint_name)s",
    "fk": "fk_%(table_name)s_%(column_0_name)s_%(referred_table_name)s",
    "pk": "pk_%(table_name)s",
}
```

Persist timestamps as timezone-aware UTC instants (`DateTime(timezone=True)`). Application-generated values use UTC-aware datetimes; database server defaults use `CURRENT_TIMESTAMP` where insert timestamps are server-owned. Domain records should retain relevant creation/update and lifecycle timestamps.

## Constraints, indexes, and queries

- Prefer database-enforced foreign keys, uniqueness, and other valid invariants in addition to service validation.
- Indexes must support common organization, account, finding, asset, and time-based queries. Tenant-scoped access patterns should inform composite index design.
- Avoid speculative indexes and unbounded list queries. Paginated API behavior and data access must be compatible.
- Never rely on frontend filters for tenant isolation.

## Transactions

Use explicit transaction boundaries around a coherent unit of domain work. Request-scoped sessions commit only when the unit succeeds and roll back on exceptions. A failed unit must not leave partially committed related state. Work spanning PostgreSQL and Redis, object storage, or cloud APIs cannot assume one distributed transaction; define retry/idempotency and recovery behavior in the owning phase. PostgreSQL's default `READ COMMITTED` isolation is retained unless a documented domain requirement needs stronger isolation. Sessions are short-lived and never shared between requests or worker tasks.

## Migrations

- Alembic migrations are the sole schema evolution mechanism.
- Review autogenerated migrations; do not treat generated output as automatically safe.
- Migrations must be ordered, reproducible, reviewed, and safe for existing data. Destructive or data-transforming changes need explicit handling and phase review.
- Do not edit an already-applied migration as a substitute for a forward migration.
- Migration runtime configuration is read from `CLOUDSENTINEL_DATABASE_URL`; credentials are not embedded in Alembic configuration.
